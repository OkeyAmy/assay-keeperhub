## What is tested, and why

The reconciler is a pure function of three inputs — the committed intent, the
executor's audit trail, and an independent chain observation. That is a
deliberate design choice: it means **every failure mode the demo shows is also a
unit test**, rather than something you have to take on faith from a video.

## The tests that matter most

### `UNPROVEN` is never upgraded to `VERIFIED`

The single most important property. A verifier that cannot say *"I could not
tell"* will eventually say `VERIFIED` when it means `UNPROVEN`.

```
✓ never upgrades an UNPROVEN to VERIFIED
✓ is UNPROVEN when no observer could be reached
✓ is UNPROVEN when observers fail to reach quorum
✓ is UNPROVEN when balances could not be snapshotted
✓ is UNPROVEN — not VERIFIED — when the executor reports no txHash
```

### KeeperHub issue #1840 — the idempotency wedge

A reused idempotency key replays a *cached failure*, so a retry never
resubmits. The loop looks healthy and the transaction never lands.

```
✓ gives every attempt a distinct idempotency key
✓ derives keys matching idempotencyKey for each attempt index
✓ is DIVERGENT when retries replayed a cached failure and never resubmitted
✓ detects a wedge from repeated keys even without replay flags
✓ does not flag a wedge when a later attempt with a fresh key landed
```

### KeeperHub issue #1784 — missing transaction hash

Sponsored and 7702 executions can return no `txHash`. That is not success and
not an error — it is an absence of evidence.

```
✓ is UNPROVEN — not VERIFIED — when the executor reports no txHash
✓ substitutes the zero hash when no transaction was reported
✓ [Solidity] test_write_acceptsZeroTxHashAsUnproven
```

### Reported success, onchain reality

```
✓ is DIVERGENT when the executor claims success but the chain reverted
✓ is DIVERGENT when a "successful" transaction changed nothing
✓ is DIVERGENT when a balance moved outside the declared bounds
✓ is DIVERGENT when calldata does not match the commitment
✓ is DIVERGENT when the amount is off by a decimal
```

## Test discipline

Two conventions are enforced by hooks in this environment, and both improved the
suite:

**Every non-trivial assertion cites its source.** Each carries a
`blindfold: <source> — why` annotation naming where the expected value comes
from: `contract` (a declared interface), `issue` (a KeeperHub tracker item),
`doc` (their API documentation), `golden` (a generated vector), or `invariant`
(a property the design must hold).

```ts
// blindfold: issue — KeeperHub #1840, distinct keys are what make a retry an actual resubmission
expect(new Set(keys).size).toBe(4);
```

**No vacuous assertions.** Three tests originally asserted only
`expect(...).toBeNull()`, which would also pass against a guard that never ran.
They were rewritten as boundary pairs asserting a concrete code on the other
side:

```ts
it('permits exactly the cap and rejects one unit above it', () => {
  expect(guard.check(intent(), 5_000_000n)).toBeNull();
  expect(guard.check(intent(), 5_000_001n)?.code).toBe('VALUE_CAP');
});
```

## Running

```bash
pnpm verify              # everything, in one gate
pnpm test                # TypeScript only
pnpm test:contracts      # Solidity only
pnpm test:watch          # Vitest watch mode

pnpm --filter @assay/contracts test:gas          # gas report
FOUNDRY_PROFILE=ci pnpm test:contracts          # 5,000 fuzz runs
```

Coverage thresholds are enforced on `packages/core` — 90% statements, lines and
functions, 85% branches. The reconciler is the product; it does not get to be
partially tested.

## What is *not* covered by automated tests

Stated plainly, because pretending otherwise would be the exact failure mode
this project exists to catch:

- **Live KeeperHub API calls.** `packages/keeperhub` is exercised against its
  documented contract, not against their servers. `pnpm --filter @assay/runner
  doctor` performs the live check instead.
- **The dashboard.** Build-verified and manually exercised; no component tests.
- **The reasoner.** Optional, non-deciding, and untested — it cannot influence a
  verdict, so a failure there degrades explanations only.
